## Run 101 — 2026-07-03 — RESEARCH

**What I investigated:** Seed-aligned Pi Pulse trust surfaces: live preflight APIs, scheduled runner paths, stdout failure parsing/detail, per-incubator Ollama/Qwen feedback payloads, mounted play/API fallthrough behavior, and current incubator slot state.
**Key finding:** Manual trust gates are now mostly working, but scheduled preflight blocks still disappear from user-facing history. `startLabRun()` returns `null` on failed preflight and the host scheduler simply returns; the incubator scheduler logs `preflight blocked run` to the server console and continues without writing a run-history event, advancing `lastScheduledRun`, or rescheduling. A blocked enabled slot would retry every minute with no visible history row. Live evidence: `/api/run/preflight` defaults to passing Codex, `/api/run/preflight?runner=claude` returns JSON `ok:false` for a missing Claude model, `/api/incubators/race-whisperer-predict/preflight` rejects `fable`, `/api/runs` and race-whisperer runs expose FAILED rows with multiline `detail`, and unknown `/api/*` returns JSON 404 rather than `index.html`.
**Implication:** The next build should preserve the working manual preflight/error-detail path and close the automation gap: skipped scheduled attempts need to be persisted as first-class run-history events, not console warnings. This is now the highest-leverage trust fix because it makes unattended failure impossible to miss.
**Suggested next move:** MUTATE: add a shared `appendSkippedRunEntry`/`recordPreflightBlock` helper that writes a compact `FAILED` or `SKIPPED` run block with the failed check detail to the target run log, call it from both host and incubator schedulers when preflight blocks a due run, update `lastScheduledRun`/`nextRunAt` so blocked schedules do not hammer every minute, and surface recent skipped/preflight-blocked status in ProjectPanel.
