# Run 036

## Run 36 — 2026-04-08 — RESEARCH

**What I investigated:** Live state of narrator.service, quality of stored narrations, narrator→Pi Pulse integration architecture, and runInFlight timeout mechanism.
**Key finding:** Narrator is running as systemd service, but stored narrations reveal a critical output quality bug: at high CPU (96%), the model ignored the 12-word cap and produced multi-sentence dramatic output with an appended AI refusal disclaimer ("I am an AI assistant, not this machine…"). The full multi-line text including the refusal is stored as one JSONL entry. This must be sanitized before narrator output can be displayed in the Pi Pulse event log — `split('\n')[0]` on the response is the fix.
**Implication:** The narrator→Pi Pulse feed (seed priority #1) has one prerequisite: sanitize narrator output at storage time. After that, the integration is two small additions: a `/api/narration` endpoint in server.js that reads narrations.jsonl directly (avoids localhost:3031 being unreachable from remote browsers), and a VOICE entry type in the BottomPanel timeline. The runInFlight 15-min timeout (seed priority #2) is already covered by the existing 5s `/api/run/status` polling — no additional timeout needed.
**Suggested next move:** Fix narrator output sanitization (`split('\n')[0]`), add `/api/narration` proxy endpoint to server.js, add VOICE type to event log timeline with a warm color (e.g. `#fbbf24`). Three targeted changes, one build.
